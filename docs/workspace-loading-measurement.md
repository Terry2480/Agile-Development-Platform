# 工作台首屏请求调度 A/B 测量（2026-11-24）

## 结论

第一步（只改客户端请求调度）**值得保留**。同一份生产构建、两轮各 12 对交替样本合并（24 对）：

| 指标 | 旧调度 median | 新调度 median | 配对差（旧-新） | 相对 |
| --- | ---: | ---: | ---: | ---: |
| 第一张任务卡 | 128.6 ms | 104.7 ms | -22.95 ms | **-18.6%** |
| 选定默认项目 | 95.0 ms | 77.25 ms | -8.8 ms | -18.7% |
| `/api/projects` 发出→TTFB | 33.8 ms | 18.0 ms | -13.1 ms | **-46.7%** |
| `/api/tasks` 总耗时 | 34.7 ms | 21.55 ms | -12.9 ms | **-37.9%** |

两轮单独看方向一致：卡片分别 **150.95→121.0 ms** 和 **121.95→96.15 ms**。绝对耗时随机器变热下降，但相对收益稳定在 18–21%。

默认使用新调度；`?sched=legacy` 保留旧调度，用于回退和以后复测。任务卡、附件系统、接口协议和权限检查都没有改。

## 测量环境

- 服务：`next start`，生产模式，`http://localhost:3113`。
- 构建：`npx next build --webpack`。Turbopack 在当前工作区因 `node_modules` 是指向项目根之外的 junction 而 panic（`Symlink [project]/node_modules is invalid`），这是环境问题；A/B 两边使用同一份 Webpack 生产构建，因此对照有效。
- 数据：隔离库 `agilecampus_ws_perf_20261124`，从测试库模板克隆后运行 `npm run db:seed`，4 个演示账号、2 个项目、13 个任务、6 条聊天、3 条通知、1 个私信会话。测量结束后删除该库和临时上传目录。
- 登录：生产模式下登录 POST 要求 HTTPS 来源，测量脚本改为在隔离库写入一条会话，用 `agile_session` Cookie 直接打开工作台；只测 GET 读取链路，未测登录本身。
- 浏览器：Edge 无头，1440×1000，每个样本清缓存、清 Cookie、重新导航。

## 方法

- 交替顺序：偶数对先旧后新，奇数对先新后旧；每轮预热 2 对丢弃，正式 12 对；共两轮 24 对。
- 四个时间点：
  1. 脚本就绪：工作台首次挂载（`ws:script`）。
  2. 身份确认：`/api/auth/me` 提交后（`ws:auth`）。
  3. 选定默认项目：`.ws-proj.active` 出现（DOM 观察，不是 `selectProject` 调用时刻）。
  4. 第一张任务卡：`#ws-center .ws-task-card` 出现（DOM 观察）。
- `/api/projects` 与 `/api/tasks` 的 start / TTFB / end 来自 Resource Timing；`encodedBodySize` 用于排除“响应体变大”这种解释。
- 转移测试：卡片出现后立即点“团队聊天”，再点图标栏“通知”，记录点击到 `.ws-msg` / `.ws-notif` 出现的时间。
- 等价性：逐对比较选中项目名、卡片数、第一张卡标题；24 对全部一致。

## 结果（24 对合并）

| 指标 | 旧 median | 旧 p95 | 新 median | 新 p95 | 配对差 median |
| --- | ---: | ---: | ---: | ---: | ---: |
| 脚本就绪 | 38.75 | 56.0 | 40.25 | 60.3 | -2.1 |
| 身份确认 | 51.4 | 70.2 | 52.15 | 76.7 | -3.2 |
| 选定默认项目 | 95.0 | 110.1 | 77.25 | 116.3 | 8.8 |
| 第一张任务卡 | 128.6 | 162.8 | 104.7 | 158.6 | 22.95 |
| projects 发出→TTFB | 33.8 | 43.7 | 18.0 | 27.0 | 13.1 |
| projects 总耗时 | 34.35 | 44.3 | 18.4 | 27.6 | 13.25 |
| auth→projects 发出 | 2.65 | 7.5 | 2.5 | 9.3 | 0.3 |
| projects 结束→选定 | 2.8 | 4.5 | 2.6 | 5.3 | 0.35 |
| 选定→第一张卡 | 40.0 | 52.0 | 25.8 | 42.7 | 12.8 |
| tasks 总耗时 | 34.7 | 45.2 | 21.55 | 37.5 | 12.9 |
| 卡片后切聊天 | 5.05 | 6.8 | 22.5 | 32.7 | -16.5 |
| 卡片后切通知 | 1.7 | 2.4 | 1.85 | 2.7 | -0.1 |

两轮单独值：

| 轮次 | 卡片 旧→新 | projects TTFB 旧→新 | 切聊天 旧→新 |
| --- | ---: | ---: | ---: |
| 第一轮 | 150.95 → 121.0 | 37.85 → 21.75 | 5.1 → 24.7 |
| 第二轮 | 121.95 → 96.15 | 28.2 → 17.1 | 5.05 → 21.15 |

## 怎么解释

- `auth→projects 发出` 两边都在 2.5–2.7 ms，说明收益不是“项目请求提前发了”，而是**发出去之后不再和另外五个请求抢服务端/事件循环**。
- `projects 结束→选定` 只有 2.6–2.8 ms，说明旧耗时不是 React 渲染项目列表造成的；把项目列表渲染当成主因会优化错地方。
- 第一张卡的收益大致分成两半：projects 的 TTFB 少约 13 ms，选定后 tasks 的请求+渲染少约 13 ms。
- 旧调度卡片前有 15 个 `/api` 请求，新调度 8 个；差的 7 个正是被延后的团队、概览、通知、待办、私信，以及选项目后的聊天、文件、详情/日志中的一部分。
- 新调度 104.7 ms 的卡片仍由串行链构成：脚本在约 40 ms 就绪、auth 在约 52 ms 完成，projects 单独耗时约 18 ms，tasks 约 21.5 ms，卡片在 104.7 ms 出现。下一步要再降，主要只能动 projects/tasks 的服务端成本或去掉一次串行往返。

## 转移测试

- 卡片后第一次切聊天：旧 **5.05 ms**（旧调度选项目时已把聊天拉好）→ 新 **22.5 ms**（按需拉取），**多 16.5 ms**。
- 卡片后切通知：旧 1.7 ms → 新 1.85 ms，基本不变。
- 判断：聊天确实承担了一部分按需加载成本，但 **16.5 ms < 首屏省下的 22.95 ms**，且通知没有转移；同一项目内再次切聊天会复用已加载数据，不再付这十几毫秒。符合“没有把同等卡顿转移过去”的要求，但这是可见的取舍。
- 如果希望第一次切聊天也接近旧体验，可在“团队聊天”标签的 hover/focus 时做一次预取，仍然遵守“不因每次选项目就拉聊天”的规则；这次没有做。

## 实现要点与回归修复

- 新调度阶段：auth 后只发 projects；选项目后只发当前分区主资源（tasks / chat / detail），再把右侧栏需要的 tasks、detail、activities 作为第二轮补上；首屏就绪后按“通知+私信 → 统计+待办 → 团队”三波补用户级数据，再启动轮询。
- 聊天、文件不再随每次选项目拉取；聊天只在聊天分区首次进入时拉取并轮询，文件保持按需。
- 审查中修复了一个回归：聊天/概览视图不加载 tasks 时，右侧栏进度会一直停在“正在加载进度…”。现在这两个视图的右侧栏补齐包含 tasks，视图切换时也会补齐当前分区所需资源。
- 深链 `?project=`、快速切换的迟到响应拦截（`RequestGate`）、权限检查和项目选择规则保持不变。
- 加载态：角标未加载显示中性加载点；通知/待办/私信视图、右侧栏进度/日志、状态栏成员数、管理面板、今日页都区分“未知”和“0”。

## 是否进入第二步

- 第一步已经把卡片从约 129 ms 降到约 105 ms；`/api/projects` 单独 TTFB 仍有 18 ms，`/api/tasks` 21.55 ms。若继续在本机优化，优先做 **2a：拆 `/api/projects` 的查询与首屏字段**，因为它影响所有调用入口；当前数据不支持直接做 2b 服务端首屏——本机没有网络 RTT，2b 省下的主要是串行往返，无法用这份本地数据证明收益。
- 但真实部署每跳都有 RTT，`auth→projects→tasks` 仍是两次串行往返；在测试服务器上用真实网络复测后，如果 RTT 占比明显，再做 2b 才有依据。也就是说：**本机数据支持保留第一步，但不支持用本机数据否决或批准第二步。**

## 限制

- 绝对值和用户给出的 327 ms 基线不可直接比较：数据量、构建方式、是否包含登录、机器状态都不同。可比较的是同一构建内的配对差值，以及“争用发生在服务端/事件循环”这一结论。
- 两轮之间的绝对耗时从 151/121 降到 122/96，是机器变热/系统缓存带来的；相对收益稳定，说明结论不依赖某一次的绝对值。
- 测量完成后只补了一个后台补齐的去重判断（用户提前点开面板时复用进行中的请求，不再 abort 重发）；它在第一张卡之后才执行，不改变首屏计时。
- 24 对样本的 p95 仍有抖动，结论以 median 和配对差为准。
- 生产模式下登录 POST 需要 HTTPS；本次没有测登录，只测登录后的工作台读取链路。
- `npm test` 需要显式 `DATABASE_URL=/agilecampus_test_20261112` 才能跑 `phase-2-baseline`；按该库运行时 114 通过、2 个按约定跳过。`npm run lint` 通过。`npx next build --webpack` 通过；`npm run build`（Turbopack）在本工作区因 junction 环境问题失败，与本次代码改动无关。
