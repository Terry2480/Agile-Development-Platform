# AgileCampus MVP 设计文档（策一：Agent 纵贯线）

日期：2026-07-02
状态：已获批准

## 1. 背景与定位

AgileCampus 是面向高校实验室团队、课程团队、学科竞赛团队的轻量化敏捷项目管理平台。本文档定义第一阶段（MVP）的设计。

已确认的约束与决策：

- **性质**：真实产品。今年供多团队内部试用（几十到百人规模），未来目标市场化。
- **范围**：本阶段只做 Web 版项目管理工具，不做消息/IM 功能。
- **核心形态**：Agent 驱动的项目管理——对话即界面，Agent 为主入口；看板/列表是 Agent 操作结果的可视化与人工微调区。Agent 只管理项目，不代做实际工作。
- **模型**：DeepSeek（OpenAI 兼容 API）。
- **资源**：1 人 + Claude Code，1-2 个月出 MVP。
- **暂不考虑**：云存储、成本优化（市场化阶段再议）。

## 2. MVP 范围

### 包含

1. **地基**：账号（邮箱+密码登录）、团队与邀请码、三角色（admin / teacher / student）
2. **骨架**：项目 → 里程碑 → 任务（负责人、截止日、状态），看板视图（todo / doing / done 三列）
3. **灵魂**：对话式 Agent，六个工具（tool calling），写操作一律人工确认后落库

### 明确舍弃（后置到 MVP 之后）

- 自动周报、风险提醒、老师反馈流、任务验收流
- 文档管理、成果链接管理、项目复盘、档案导出
- 老师多项目总览页（"老师瞭望台"，为 MVP 后第一个增量）
- SSO、消息通知

## 3. 整体架构

```
浏览器
  ├── 对话区（Agent 主入口，流式回复 + 操作确认卡片）
  └── 看板/列表区（可视化 + 人工微调）
        │
Next.js 单体应用（App Router，前后端一体）
  ├── 页面与 API（Server Actions / Route Handlers）
  ├── Agent 编排层（Vercel AI SDK + tool calling）
  │       └── DeepSeek API（OpenAI 兼容协议）
  ├── 权限层（团队隔离 + 三角色）
  └── Drizzle ORM
        │
PostgreSQL（唯一数据源）
```

### 技术选型

| 部位 | 选择 | 缘由 |
|---|---|---|
| 框架 | Next.js（App Router） | 一人全栈，前后端一语言一仓库 |
| 数据库 | PostgreSQL + Drizzle ORM | 关系模型契合 PM 数据；Drizzle 轻量、类型安全 |
| 认证 | Auth.js，邮箱+密码 | 内部试用够用，日后可加 SSO |
| AI | Vercel AI SDK + DeepSeek | AI SDK 流式 UI 与 tool calling 现成；OpenAI 兼容接口，换模型只改配置 |
| 校验 | Zod | 系统边界（API 入口、Agent 工具参数）schema 校验 |
| 部署 | 单机 Docker Compose（Next.js + Postgres） | 内部试用国内访问 DeepSeek 低延迟 |

架构原则：单体不拆微服务；Agent 是应用内一个编排模块，不是独立服务。

## 4. 数据模型

八张主表：

| 表 | 内容 |
|---|---|
| `users` | 用户（邮箱、密码哈希、姓名） |
| `teams` | 团队（名称、邀请码） |
| `team_members` | 用户↔团队关系，含角色（admin / teacher / student） |
| `projects` | 项目（属于团队；名称、描述、状态、起止日期） |
| `milestones` | 里程碑（属于项目；标题、目标日期、状态） |
| `tasks` | 任务（属于项目，可挂里程碑；标题、描述、负责人、截止日、状态 todo/doing/done、优先级、排序位） |
| `conversations` | Agent 对话会话（属于项目或团队级） |
| `messages` | 对话消息（角色、内容、工具调用记录 JSON） |

设计要点：

- **团队为隔离边界**：一切查询自团队起步，跨团队不可见。多租户之基从第一天建立。
- **任务状态仅三档**：高校场景不需要复杂工作流，看板三列。
- **对话入库**：全量对话与工具调用记录存 `messages`，为日后 AI 周报/复盘留原料。
- **不建策一舍弃功能的表**，需要时再做 migration。

## 5. 权限模型

| 角色 | 权限 |
|---|---|
| admin | 团队设置、成员管理、一切项目操作 |
| teacher | 查看团队内所有项目与任务（无须被分配）；反馈功能后置 |
| student | 参与的项目内建任务、改任务、使用 Agent |

权限判定收敛在统一工具函数（如 `requireTeamRole()`），不散落在各接口。

## 6. Agent 设计

### 6.1 工具清单（兵器谱）

| 类 | 工具 | 职能 |
|---|---|---|
| 读 | `query_progress` | 查项目/里程碑/任务进度 |
| 读 | `list_tasks` | 按人、状态、截止日筛任务 |
| 写 | `create_project` | 从描述创建项目（含目标、起止日） |
| 写 | `decompose_tasks` | 核心能力：把目标/需求拆成任务清单（建议负责人、截止日、里程碑归属） |
| 写 | `update_tasks` | 批量修改任务（状态、负责人、延期） |
| 写 | `plan_sprint` | 把待办任务排入迭代/时间段 |

### 6.2 写操作两段式（人工确认）

1. Agent 调用写工具，仅产出**草案**，不落库。
2. 对话流中渲染**确认卡片**：任务清单可勾选、可编辑字段。
3. 用户确认 → 服务端在落库一刻执行权限校验，事务写入 → 看板即时刷新。
4. 用户可修改后确认，或驳回作废。

读操作直接执行，即问即答。写操作落库时不信任 Agent 输出，一律重新校验权限与数据合法性。

### 6.3 上下文供给

每轮对话在系统提示词注入当前项目快照（项目概要、里程碑、成员名录、任务统计）。快照有大小上限，超限时只注入统计摘要，细节由读工具现查。

### 6.4 错误处理

- DeepSeek 超时/失败：对话中明示错误并允许重试；不静默失败，不自动重试写操作。
- 工具参数非法：Zod 校验拦截，错误回喂 Agent 自纠一次，再失败则如实呈报用户。
- 确认卡片过期：落库前做版本校验，数据已被他人改动则提示刷新，不盲目覆盖。

## 7. 测试方略

- **单元测试**：权限函数、各写工具的落库逻辑（不含 LLM 调用）。
- **集成测试**：以录制的工具调用 JSON 回放（fixed LLM replay）测对话→工具→落库全链路，不依赖真实 DeepSeek 调用。
- **手动验收**：六个工具各走一遍真实对话场景的验收清单。

## 8. 验收标准（MVP 完成的定义）

1. 用户可注册、登录，创建团队并以邀请码加入，角色生效。
2. 用户可通过传统界面创建项目、里程碑、任务，并在看板拖拽改状态。
3. 用户可在对话中让 Agent 完成：查进度、筛任务、建项目、拆任务、批量改任务、排迭代——写操作均出现确认卡片，确认后正确落库且看板刷新。
4. 越权访问（跨团队、越角色）被统一权限层拒绝。
5. LLM 失败时界面有明确错误提示，无静默失败。
6. 单元与集成测试通过；Docker Compose 单机可部署运行。
